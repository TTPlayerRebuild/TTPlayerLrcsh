## 3. 本次实测确认的差异

### 3.1 歌曲 ID 的 32 位转换——优先修复

原版 `6035249B` 使用其二进制链接的 `atoi`；当前 `src/protocol.cpp:26` 用 `strtol`。超出有符号 32 位上限时，两者不一致：

| 服务器 ID 文本 | 原 DLL 下载请求 | 重建 DLL 下载请求 |
|---|---|---|
| `4294967295`，本次固定歌手/歌名 | `Id=-1&Code=1779067794` | `Id=2147483647&Code=-1373917294` |

搜索列表显示的歌手、歌名完全一样，因此只比较搜索回调会漏掉这一问题。**ID 和校验码都变了，旧协议服务器可能拒绝下载或定位到错误记录。** 本次本地服务器只记录请求，没有模拟真实服务端的签名拒绝，不能写成已证明某个实服因此下载失败。

建议：按原 DLL 可观察行为实现明确的 32 位整数解析，不依赖当前 CRT 的溢出策略，也不使用有符号溢出的未定义行为。补测 `INT_MAX` 两侧、`UINT_MAX`、负值、超长数字、空白和数字后缀；同时比较最终下载 URL。错误码也共用 `LegacyInt`，应一并评估。

### 3.2 XML 数字实体改变签名字节——优先修复

原版 `60355612` 的实体处理与新 XML 解析器不等价。原版保留本次测试的数字实体原文，新版 `src/xml.cpp:52` 将其解码：

| 输入 artist，固定 `id=123`、`title=title` | 原 DLL 回调 / Code | 重建 DLL 回调 / Code |
|---|---|---|
| `A&#65;B` | `A&#65;B` / `-1137079660` | `AAB` / `-552387306` |
| `A&#x1F600;B` | `A&#x1F600;B` / `318211926` | `A😀B` / `399864500` |

五个常见命名实体 `&lt; &gt; &amp; &quot; &apos;` 和未知实体 `&copy;` 的测试则一致。

当前下载 Code 算法本身没有在这些样本中算错；**参与计算的字符串已经被新解析器改变**。仅验证 Code 函数的普通输入不足以发现它。

建议：明确区分旧协议属性解码与通用 XML 解码。下载保留原版语义的属性字节；如要改善显示，使用独立显示字段，不能拿显示后的文字反算旧协议 Code。不要为追求标准 XML 支持而无条件改变旧服务器的签名输入。

### 3.3 服务器刷新丢失内存配置

原版 `60351BE8` 是按出现的节点更新相应字段；当前 `src/catalog.cpp:43` 整体替换、补空第二槽，并把未出现的 extra 清空。

| 刷新响应 | 原 DLL | 重建 DLL |
|---|---|---|
| 原有两个 server，响应只含一个 server | 第一项更新，第二项在本会话仍为旧值 | 第二项名称和 URL 变空 |
| 原有 extra，响应不含 extra | 保留旧 extra | 清空，`GetExtra` 返回 `E_FAIL` |
| 响应只含 extra、不含 server | 更新 extra，保留服务器，不写盘 | `Parse` 因没有 server 失败，extra 更新丢失 |

“保留第二项”指当前会话的内存行为；原版单节点响应写入磁盘后，文件本身仍只有一个 server，不应混淆内存合并与持久化。

建议：分别处理 server 槽更新、extra 更新和写盘条件，不以“必须至少一个 server”阻止合法的 extra 会话更新。保留新版刷新失败不破坏已有可用配置的改进。

### 3.4 服务器 INI 写回会删掉扩展内容

原版 `60351BE8` 调用 `60356C68` 移除根 `query_url` 属性、移除 extra 子节点，再保存解析后的完整文档。当前 `Save` 只根据前两个 `Service` 重新生成简化 XML。

本次响应含根 `version`、server 的 `custom` 属性、第三个 server、`custom` 子节点。原版全部保留这些扩展内容；新版全部丢弃，只留下两个 server 的 name/url。两者都不持久化 extra。

建议：运行接口仍只使用前两个服务，但写回保留响应文档的其余有效节点/属性；继续采用新版临时文件、FlushFileBuffers、原子替换。当前 XML 结构不保留文本和注释，若要求完整文档保真，需扩展表示或保留合适的原始片段。`Save` 的失败也应有可诊断记录，不能把内存更新当成持久化成功。

### 3.5 空歌手参数不兼容

原入口 `60352282` 只要求 title 指针非空；`603536F2` 把空 artist 转为空串。

- 原 DLL：`Find(nullptr, L"title")` 返回 `S_OK`，发出搜索并得到结果。
- 当前 `src/plugin.cpp:127`：返回 `E_POINTER (0x80004003)`，不发请求。
- 两版对空 title 指针都返回 `E_POINTER`，本次已核实。

建议：artist 为空指针按空字符串处理，保留 title 的原约束。当前重建宿主传的是 `std::wstring::c_str()`，通常绕过此问题；第三方/原接口调用仍应兼容。

### 3.6 忙碌时的新命令不兼容

原版 `60352443` 记录新命令并设置事件，事件还参与当前 HTTP 等待的取消；没有 `ERROR_BUSY` 拒绝路径。原版并非完善的任务队列，旧请求也可能产生取消错误回调。

本次故意让首个搜索延迟 1 秒，在 200 ms 时再次 Find：

- 原 DLL：第二次返回 `S_OK`，旧请求收到“连接服务器失败”回调，随后执行第二次搜索。
- 新 DLL：第二次返回 `0x800700AA (ERROR_BUSY)`，只执行第一次。

建议：旧 Search 接口恢复“新命令替换/取消旧任务”的可用性，用操作代数区分结果归属，避免旧任务覆盖新任务。不要重引入原版的 `TerminateThread`。是否保留旧取消错误回调应明确为兼容策略，不能在自动搜索中让旧错误结束新任务。

### 3.7 HTTP 状态与空正文

原版 `60351585` 对状态 `<400` 可返回请求句柄继续读取；当前 `Native` 仅在 200 读取正文，`Transport::Get` 也仅接受 200。

- 本次 201、206 携带完整有效歌词 XML：原 DLL 返回结果；新 DLL 返回“下载时发生未知错误”。
- 200 空正文，搜索和下载分别测试：原 DLL 为“下载时发生未知错误”；新 DLL 为“连接服务器失败”。

建议：恢复旧协议实际需要的成功状态处理，保留 HTTP 状态供错误层判定；对 206 应验证返回内容完整性，不能盲目把截断正文当有效歌词。新版对 301/302/303/307/308 的受控重定向和 HTTPS 禁止降级应保留。空正文不应和未建立连接混为同一原因。

### 3.8 重复属性、NUL 等宽容行为

- `<lrc id="1" id="2" .../>`：原 DLL 取第一项，下载 `Id=1`；新版直接拒绝重复属性。
- 歌词正文内嵌 NUL：本次原 DLL 返回去除该 NUL 后的正文，新版报无效数据。
- UTF-8 BOM 正文、含 NUL 的附加头、未知实体：本次所测可观察回调一致。

建议：重复属性可在旧协议解析策略中保留第一项，资源上限继续有效。内嵌 NUL、错误 UTF-8 等异常输入应按真实服务器样本决定兼容策略，不必为了复刻原版宽容而取消所有校验。BOM/附加头的单个样本一致不代表所有损坏编码均一致。

## 4. 源码确认、仍需故障注入或真实宿主测试的项目

以下与第 3 节的差分实测分开记录，不宣称已在原版完整 GUI 复现。

### 4.1 初始化就绪与失败回滚

原版 `603520CD` 创建工作线程后等待就绪事件最多 5 秒，读取线程初始化 HRESULT。工作线程 `60353322` 会先建立 WinINet 会话，再确认就绪。

现在 `Initialize` 在 `CreateThread` 成功后立即返回 `S_OK`；`Transport` 在工作线程里创建，WinINet 会话更延迟到每次请求。失败从“初始化失败”变成“异步搜索失败”。若外层工作循环异常退出，State 没有标记工作线程已不可用，后续 Find 仍可能入队却永远无人处理。

此外，Callback 已写入 state 后若分配、模块固定或创建线程失败，未回滚 callback；重复 Initialize 会被当成已经初始化。当前还持有 `state_->mutex` 调用外部 `QueryInterface/Release`，存在外部重入锁风险。

建议：事务式初始化、就绪事件/结果、失败状态和清理回滚；不要持内部锁调用宿主方法。若保留现代延迟建连，应明确区分“工作线程可用”和“网络已准备好”，旧接口不能报告虚假的线程成功状态。

### 4.2 最后一次 Release 的无限等待

原析构 `60351FE3` 发退出命令，等 500 ms，失败后强杀线程。新版取消请求、不强杀线程并固定 DLL，是正确改进；但 `src/plugin.cpp:88` 使用无消息泵的 `WaitForSingleObject(INFINITE)`。

原宿主结果回调 `0043B332` 会进入 `0043BAA3`，调用 `SetDlgItemTextW`、`SendMessageW` 等同步 UI 操作。关闭路径 `0043BB8D` 通过 `004045F3` 释放 Search。若 UI 正在最后释放 Search，而工作线程正等 UI 处理同步消息，两边可以互相等待。

重建宿主 `online_search.cpp` 将 session 释放放在后台，并在回调更新前检查 canceled，降低了自身 UI 的风险；这不能证明 DLL 对原版宿主同样安全。

建议：设计兼容原宿主的有界退出与消息处理/延后回收机制，配合 callback 生命周期和模块引用验证。不能仅删除等待让旧 callback 继续访问已关窗口，也不能退回强杀线程。验收必须包括原版 GUI 在响应到达时关闭搜索窗口、换歌和退出播放器。

### 4.3 Cancel 与回调之间的竞态

`Alive()` 检查结束后才调用 Callback，两步不原子。Cancel 可能在两者之间返回，之后仍开始一个回调。`busy=false` 也在回调之前发布，另一个线程可以先提交下一次请求。

建议：定义清楚“Cancel 返回后”的保证，增加操作代数、回调准入和在途回调管理；不能简单在持有 state 锁时执行外部回调，否则回调内 Download/Cancel/Release 会死锁。现有回调内最终 Release 用例应保留。

### 4.4 代理、认证和请求头并未完全复刻

- 原版 `60351585` 对 407 和 401 均有一次设置账号/密码后重试分支；新版 Native 只显式处理代理 407，并抑制服务器认证。HTTPS 另走 `ttp_https`，不能按原 WinINet 实现推定一致。
- 实际抓到原 DLL 发送 Referer 和旧 Accept 列表；新版缺少它们，并增加 `Cache-Control: no-cache`。Native User-Agent 一致；HTTPS ABI 5 默认 User-Agent 另有实现。
- 原版 worker 复用 WinINet 会话；新版每次请求重建会话，仅显式 Cookie jar 随 Search 保留。
- 原发送阶段有 60 秒等待；新版设置每阶段 10 秒，另有每跳 65 秒检查。重定向重置计时，不能把它称为整次操作严格 65 秒上限。

建议：补直接连接、系统代理/PAC、显式代理、407、必要的 401、跨域跳转和断网/慢读测试。保留新版不把代理凭据无条件送给目标服务器的限制；若旧服务确实需要认证，用明确作用域实现。按实际服务需求补旧请求头，而不是恢复所有旧缓存和自动认证行为。

### 4.5 配置来源与扩展接口边界

Configure 明确指定服务后跳过远端 svrlst 是有意设计，但 GetExtra 仍取 DLL 全局 catalog 的 extra，可能把旧目录附加链接展示在另一个显式服务的结果旁。需为显式服务规定独立 extra/清空策略并测试。

原版下载时重新读取全局服务器槽；新版使用搜索时保存的 Service。在并发首次刷新与下载交错时可能不同。保持搜索、结果和下载属于同一服务器更合理，应记录为有意改进，并补并发测试，不建议机械恢复可能的服务器错配。

## 5. 不建议原样恢复的旧行为

| 原版行为 | 建议 |
|---|---|
| 超时后 TerminateThread | 保留协作取消、模块固定和正确释放；补安全退出方案 |
| svrlst 返回空内容时删除 INI | 保留已有文件，避免瞬时故障丢失用户配置 |
| ANSI/MAX_PATH 配置路径 | 保留 Unicode 路径；原子保存中的临时路径仍需长路径专项测试 |
| 从 ttpcomm ordinal 302 生成 `ci` 并附加到请求 | 当前确实省略；默认维持不发送设备标识。只有确认受控旧服务需要时才设计可选兼容，不擅自开启 |
| 无响应体/结果数/深度边界 | 保留 2 MiB、10,000 行、XML 深度/节点/属性上限，补上下边界测试 |
| WinINet 自动全局 Cookie 与认证 | 保留按 Search 隔离 Cookie、受控重定向和凭据边界；跨子域 Cookie 不一致需明示 |
| 原版 HTTPS 能力有限 | 保留 `ttp_https` ABI 5、证书验证和禁止降级 |

原版宽容输入、旧 CRT 行为和已知线程缺陷不能简单视为一个整体。应恢复影响有效请求、结果和宿主调用的契约，同时保留有意的健壮性改进。

## 6. 还缺的系统与端到端验收

1. 原版播放器实际加载新 DLL：自动搜索、手动搜索、切换两个服务器、重试下载、关闭窗口、快速换歌、最终退出。ABI 探针不能替代完整界面验证。
2. XP 真实运行：上轮 Guest Control 超时，静态导入审计通过不能代表实际运行通过；还需 HTTP 与 `ttp_https` ABI 5 的完整搜索/下载。
3. Win7：基础流程已测；本次 ID/XML/刷新边界及退出并发尚未在 VM 重跑。
4. Windows 10：按用户安排以 Win11 代验，记录为代验，不写成原生 Win10 已验证。
5. 部件组合：歌词 DLL 与支持 ABI 5 的 HTTPS DLL 搭配、缺失/旧版 HTTPS DLL 时的明确回退行为，以及原版宿主的 ttpcomm 共存。
6. 发行流水线：本地打包验证和 Action 静态检查已做，但不等于远端 Action 或正式发布已成功。本次没有重新查询远端发行状态，也没有触发发布。

## 7. 建议实施顺序

| 顺序 | 工作 | 完成标准 |
|---|---|---|
| 1 | 修正 32 位 ID 和旧 XML 属性/签名字节 | 本次 ID、十进制/十六进制实体样本下载 URL 与原 DLL 一致，NCAB 既有正常场景不回退 |
| 2 | 恢复空 artist、忙碌命令替换；引入操作代数 | 第二次请求可执行，旧结果/旧错误不覆盖新任务，原调用约束明确 |
| 3 | 完成初始化、回调和释放生命周期 | 故障注入不留不可用对象；原版 GUI 关闭/换歌/退出无互锁、迟到 UI 访问和模块卸载问题 |
| 4 | 修复目录增量更新和 XML 保存 | 单服务器/仅 extra/扩展节点样本符合原版可观察行为；失败不破坏已有文件 |
| 5 | 对齐有效 HTTP 状态、错误映射和必要网络兼容 | 201/206、空正文、代理、认证、超时有明确结果；保留证书和凭据限制 |
| 6 | 完成原版宿主、XP/Win7/Win11 及发行验收 | 将“已验证”“代验”“未验证”分别记录，再更新可发布版本和验证说明 |

前三项都应在宣布“完整兼容原版”前完成。没有可靠依据给出整体完成百分比：正常样本通过率无法量化生命周期与边界兼容度。
